## 2. IMPLEMENT FUNCTIONAL Save_Memory

Create a single canonical memory interface:

`Save_Memory.saveMemory(event, authorizationContext)`

The implementation must use the existing SQLite WAL persistence layer.

Required behavior:

1. Accept an explicitly submitted memory event.
2. Preserve the supplied content verbatim.
3. Preserve Unicode, punctuation, line breaks, symbols, and original ordering.
4. Record source, timestamp, project, device profile, and schema version.
5. Generate a unique event ID.
6. Calculate a SHA-256 digest of the original payload.
7. Append the event in a transaction.
8. Link the event to the previous ledger hash.
9. Read the committed record back.
10. Independently verify its digest and chain relationship.
11. Return a structured receipt.

Do not silently normalize, summarize, paraphrase, interpret, or deduplicate the original payload.

If optional tags or categories are supplied, store them separately from the original content. Do not invent tags.

### Canonical record structure

```json
{
  "schema": "gaia.memory.event.v1",
  "event_id": "generated-unique-id",
  "sequence": 0,
  "created_utc": "ISO-8601",
  "source": "user_supplied",
  "project": "GAIA-NEXUS",
  "device": {
    "role": "operator_configured",
    "runtime": "detected_or_declared"
  },
  "payload_encoding": "UTF-8",
  "payload": "EXACT ORIGINAL USER CONTENT",
  "payload_sha256": "SHA-256",
  "previous_hash": "PREVIOUS EVENT HASH",
  "event_hash": "CANONICAL EVENT HASH",
  "authorization": {
    "user_consent": true,
    "boundary": "pending",
    "clock_capacity": "pending",
    "verification": "pending"
  },
  "status": "committed"
}
```

The example is a schema, not a pre-generated receipt. Generate actual values at runtime.

Do not store passwords, API keys, private tokens, or secret credentials in the memory payload. Redact them before persistence and explicitly report that redaction occurred.

### Memory API

Provide:

- `saveMemory(event, authorizationContext)`
- `getMemory(eventId)`
- `listMemory(query)`
- `verifyMemory(eventId)`
- `verifyMemoryChain()`
- `exportMemory(eventId)`
- `exportMemoryArchive()`

Use parameterized database queries.

Use transaction boundaries and append-only records.

Corrections and removals must be represented through explicit subsequent records or a documented retention procedure, never silent history rewriting.

Repeated user submissions must remain distinguishable unless the user explicitly supplies an idempotency key.

## 6. HCCGN UNIVERSAL CLOCK

Reuse the existing Universal Clock implementation.

Keep temporal admissibility separate from measured computational capacity.

The current architecture specification describes:

- Nominal base interval: 100,000 ns.
- Solver interval: 500,000 ns.
- Five base intervals per solver interval.
- Monotonic one-second execution epoch.
- External UTC correlation.
- Independent lane accounting.
- Timestamped execution receipts.

Treat these as architectural targets, not guaranteed hardware timing.

Use a monotonic runtime clock for elapsed time and deadlines. Measure actual dispatch lateness, throughput, resource availability, and verification overhead.

Do not infer capacity from a configured target.

## 7. THE ARCHITECT'S AUTHORIZATION INVARIANT

Preserve:

`A = B && C && V`

Where:

- `B`: execution boundary is valid.
- `C`: clock and measured-capacity conditions are valid.
- `V`: independent verification is successful.
- `A`: authorization to execute.

Keep the internal clock and capacity measurements separately observable.

If any required condition is false, missing, stale, or unknown, withhold execution.

No boundary: no execution.

No measurement: no capacity claim.

No verification: no correctness claim.

User authorization is necessary but does not replace platform permissions, account authentication, or independent verification.
